# Reviewer dashboard

Issue #11. Written 2026-10-04.

The publish gate. Every explanation in this project is generated by an LLM from
retrieved Tafsir chunks and is invisible to readers until a human approves it —
Part 1 §20:

```
Generated → Automated Validation → Pending Review → Reviewer decision → Published
```

This is the UI for that gate: `http://localhost:3000/admin`.

## Using it

```bash
# once
printf 'REVIEWER_PASSWORD=your-password\n' >> .env

make dev          # sources .env, so both processes pick it up
```

Then open `http://localhost:3000/admin` and sign in. For each pending
explanation you get:

- **The verse**, from the verified corpus — never from the explanation.
- **The explanation under review**, in Arabic, as generated.
- **The evidence**: every chunk its `source_refs` cite, in cited order, with the
  content hash, plus the registry citation (title, author, edition, version).
- **The §20 checklist**: four checks that must all be ticked before Approve or
  Edit & Approve will save.

Actions: **Approve as generated**, **Edit & Approve** (the textarea is prefilled
with the generated text; the reviewer's version is what gets published),
**Reject**, **Escalate** (stays in the queue for someone else to rule on).

No client-side JavaScript. It is server components and two route handlers, so the
reviewer password never reaches the browser as script.

## The queue will be empty for now

Nothing writes `explanations` documents yet — that is issue #10. The queue shows
its empty state and says so. To exercise it, insert a pending explanation with a
`source_refs` entry pointing at a real chunk id, or use
`cmd/validate_retrieval` to see which chunks exist. This dashboard was verified
end-to-end against temporary fixtures that were then deleted; the acceptance
criterion ("review a pending explanation and see `review_status` flip to
`published`") is reproducible the moment there is something to review.

## How auth works, and why it is shaped like this

Two independent checks, not one:

| Layer | Mechanism | Fails as |
|---|---|---|
| Go API | `platform.ReviewerAuthMiddleware` requires `X-Reviewer-Password` to equal `REVIEWER_PASSWORD` | 401, or 503 if unset |
| Next.js | `/admin` reads an HttpOnly cookie and refuses to render the queue without it | login form |

The dashboard is a convenience; **the API is the boundary**. Hitting
`curl localhost:8080/internal/review/queue` without the header gets a 401
regardless of any cookie, so deploying the backend (issue #15) does not depend on
the web app being correct.

An unset `REVIEWER_PASSWORD` returns 503 from `/internal` and shows a setup
message on `/admin`. That is deliberate: for a system whose entire premise is
"nothing is published without a human decision", a missing secret must close the
gate rather than open it.

What this is **not**: an identity system. There is one shared password, no
per-person attribution beyond the free-text name typed at login, no expiry, no
revocation short of changing the password, and no rate limiting. Part 2 §27 asks
for Supabase Auth. Replace it when a second reviewer exists, or when "who approved
this" has to survive an audit — the cookie is the wrong place to keep a password
once either is true.

## What changed in the backend to make this work

The issue assumed the endpoints were ready. Three things were not:

1. **`ReviewerAuthMiddleware` was a pass-through.** It called `c.Next()` and
   returned 200 to anyone. Now it checks the password in constant time. This also
   means `/internal/retrieval` is gated for the first time — nothing called it
   except the future dashboard.

2. **`edit_approve` did not write the edited text.** `Decide` recorded the
   decision and set `review_status: published`, leaving the generated text in
   place. Edit & Approve was a label on Approve. The handler now accepts `text`,
   which is required for `edit_approve` and ignored by the other decisions.

3. **The queue returned raw documents.** A reviewer cannot check whether text is
   grounded in a source from a chunk id, so `PendingQueue` now resolves
   `source_refs` into chunk text and attaches the verse and the registry
   citation. Refs that no longer resolve are reported in `missing_refs` instead
   of being dropped — a citation the reviewer cannot open is not a reviewable
   citation.

Two smaller corrections, both found while verifying rather than by reading:

- **The routes were never under `/internal`.** The group was created with an
  empty prefix, so the real paths were `/review/queue` and `/retrieval/:surah/:ayah`
  — unprotected, and not the paths issue #11 documents. The group is now mounted
  at `/internal`.
- **An empty queue serialised as `null`.** The dashboard crashed on it with
  "response was not a list". `PendingQueue` now returns `[]`. `null` vs `[]` also
  affects `GET /surahs/:id/explanations` in `internal/content`, which still
  returns `null` for an empty result; the reader's client tolerates it, so that one
  was left alone rather than changed from under a different issue.

Also tightened while in there: an unrecognised decision used to write a review
record claiming the item was handled while leaving it pending; it is now a 400
and records nothing. A second decision on an already-decided item is a 409 rather
than an overwrite, which matters because the submit is a plain HTML form and
double-clicks are routine. Review records now carry `source_version`,
`prompt_version` and `model_version`, which §20 requires and `ReviewRecord` did
not have.

## Not implemented

- **§20's automatic invalidation.** If the source version changes after an
  explanation is approved, the explanation must stop being published and go back
  to review. The queue surfaces the mismatch
  (`grounding_version_mismatch`) so a reviewer sees it before approving, but
  nothing invalidates already-published content. That needs a source-change hook,
  which only exists once sources can actually be re-registered.
- **Bulk decisions.** 111 ayahs × 3 styles is ~333 explanations. Approving them
  one form at a time is the point — a bulk "approve all" would defeat the gate —
  but there is no keyboard navigation or next-item link yet.
- **Review history.** `reviews` is written and never read by the UI.
- **`prompt_version` has no producer.** It is read from the explanation and
  stored on the record, but nothing stamps it yet; issue #10 will.

## Reproducing the verification

```bash
# terminal 1
make dev

# terminal 2 — with fixtures present
curl -s localhost:8080/internal/review/queue \
  -H "X-Reviewer-Password: $REVIEWER_PASSWORD" | jq '.[].id'
```

Decisions can be driven without a browser, which is how the four outcomes were
verified:

```bash
curl -s localhost:8080/internal/review/<id>/decision \
  -H "X-Reviewer-Password: $REVIEWER_PASSWORD" \
  -H 'Content-Type: application/json' \
  -d '{"reviewer_id":"mahmoud","decision":"approve","comments":"checked"}'
```

Note the checklist is enforced by the dashboard, not the API: the API has no way
to know a reviewer read anything. Calling the endpoint directly bypasses it,
which is fine — it also means anyone with the password can publish without
reviewing, and always could. The password is the trust boundary.
